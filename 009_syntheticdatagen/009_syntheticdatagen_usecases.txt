Summary (ELI5)

Imagine you want to teach a new student (a small AI model) but all you have is a giant, messy pile of newspapers — lots of noise, typos, and junk. Instead of using that pile, you ask a very smart teacher (a big AI) to write you brand-new, clean homework problems with clear answers. The teacher can make them hard or easy, about whatever subject you like, and you throw away the ones that don't make sense or look like duplicates. The student learns from this "textbook" — cleaner and more focused than the newspaper pile — so it learns faster and better. That's synthetic data generation: let a strong AI write textbook-quality training material, then filter it carefully before using it to teach a smaller AI.
2. Use Cases (mapped to the technical card)
2.1 Phi-style Textbook Quality Pretraining (Microsoft Phi)

Microsoft's Phi series showed that a small model (~1.3B–3.8B parameters) trained on ~7B tokens of carefully curated "textbook-quality" synthetic data could match much larger models on reasoning benchmarks. The problem solved: raw web text is full of ads, redundancy, and factual noise that teaches a model bad habits. Instead, a teacher LLM (GPT-3.5/4 for Phi-1, later versions used similar pipelines) is prompted to generate clean, self-contained explanations of math, coding, and science concepts, then filtered for correctness and pedagogical quality. This is powerful because textbook content is dense — every token teaches something. The curriculum also lets you control difficulty progression, which is impossible with a fixed web dump. Why synthetic data fits: it lets you scale quality, not just quantity, and avoids the licensing traps of scraping textbooks. Phi-3 used ~3.3T tokens of heavily filtered synthetic + curated web data. The main risk is that teacher hallucinations propagate; strong filtering (LLM-as-judge, unit-test verification for code) is essential.
2.2 Self-Instruct for SFT Data (Stanford Alpaca)

Before Self-Instruct, producing an instruction-tuning dataset required thousands of human-written prompt/response pairs. Self-Instruct bootstraps this from ~175 human seeds: the teacher generates new instructions from the seeds, produces responses, and filters for quality and diversity. The problem solved: SFT (Supervised Fine-Tuning) data is expensive and slow to produce at scale. Self-Instruct cut that cost dramatically — Alpaca's 52k examples cost about $500 to generate with GPT-3.5. Why synthetic data fits: the teacher only needs to be shown a pattern (instruction → response) and can then invent endless variations in style and topic. The key insight is to keep a pool of real seeds for diversity and to filter out instructions that are too similar to seeds (to avoid overfitting) or that fail format checks. Alpaca's recipe: generate, then filter by heuristics (length, keywords like "sorry"), then deduplicate. Without careful prompts the model collapses into generating very similar instructions ("Write a poem about X").
2.3 Synthetic Reasoning Traces (DeepSeek-R1 Distillation)

DeepSeek-R1 generates long chain-of-thought (CoT) traces on difficult math and code problems; these are then distilled into smaller models (Qwen/Llama) by SFT on the (problem, reasoning, answer) triples. The problem solved: reasoning capability usually only appears at very large scale; distillation lets you inject it into a 7B model. Why synthetic data fits: you can only get this data from a strong teacher — no public dataset contains millions of long, correct, verified reasoning traces. The crucial step is answer verification: only keep traces whose final answer matches a ground-truth (e.g., a checker, unit test, or symbolic solver). Without this filter, the distilled student learns confident-sounding but wrong reasoning — worse than no synthetic data. The card's benchmark_metrics (quality pass rate, downstream delta, n-gram entropy) are exactly how you'd monitor this.
2.4 Evol-Instruct — Evolving Instructions to Higher Complexity (WizardLM)

Evol-Instruct takes a seed instruction and asks the teacher to make it harder through explicit operations: add constraints, deepen reasoning, concretize, increase steps, or rewrite in a rarer format. The problem solved: real instruction data tends to be shallow (single-step, open-ended); you need deep, multi-step examples to train a strong instruction follower. Why synthetic data fits: the teacher can systematically apply evolution operators, giving you a curriculum that goes far beyond what human annotators would write. WizardLM showed that instructions evolved to "depth 5" produced models that beat GPT-3.5 on many benchmarks. The main risk is instruction "drift" — evolutions that are incoherent or contradictory. Filtering with an LLM-as-judge that checks (a) faithfulness to the original, (b) solvability, (c) difficulty calibration is standard.
2.5 Magicoder (OSS-Instruct) — Code from Open-Source Seeds

OSS-Instruct mines real functions from open-source repositories (e.g., from The Stack) and asks a teacher to generate new coding problems inspired by them. The problem solved: existing code datasets are dominated by docstring-style "write a function X" prompts, which don't train an assistant well. By seeding from diverse real code (data structures, algorithms, libraries, edge cases), the teacher produces a much richer mix of coding problems. Why synthetic data fits: the teacher can reinterpret real code into a natural-language problem + solution, spanning styles and difficulty levels human annotators rarely cover. Magicoder's key filtering step is unit-test verification: generated solutions are executed against the seed function's behavior. If the tests pass, the example is kept; if not, it's discarded. This is the gold standard of synthetic-data filtering.
2.6 Cold Start for Math, Rare Languages, and Domains

For low-resource languages (e.g., Yoruba, Quechua) or specialized domains (medical coding, legal reasoning), there simply isn't enough human-written instruction data to fine-tune on. The problem solved: no data → no capability, even if the base model has latent knowledge. Synthetic generation with a strong teacher can bootstrap an initial instruction set (a "warm start"), which is then iteratively improved by human-in-the-loop or additional filtering rounds. Why synthetic data fits: it lets you produce a targeted corpus for a domain in days rather than years, at quality you can dial up or down. The card lists this as a key pro ("Solves cold-start for new domains"). The main risk: teacher bias against the target domain (e.g., a Claude teacher may be weak in a rare language) — mitigated by round-trip translation or multilingual judges.
2.7 Constitutional AI Revisions (Anthropic Claude)

Anthropic's Constitutional AI uses a strong "critique" model to rewrite (revise) existing responses according to explicit principles (the "constitution"). The revised data is then used for RLHF/RLAIF. The problem solved: human feedback on safety/helpfulness is expensive and slow; a principled critic can generate both the revision and the preference signal at scale. Why synthetic data fits: the teacher is literally the labeler. The card's claude_specific_notes calls this out directly: "the teacher is typically a stronger Claude checkpoint, and the synthetic data is filtered through constitutional principles." Note the deep parallel to filtering: revision is a form of generation, and the constitution is the filter. This is the purest example of "synthetic data where teacher == filter == target behavior."
2.8 Tool-Use / Agentic Traces

To train a model to use tools (search, calculators, code execution, APIs), you need millions of trajectories of the form (state, action, observation, …, final answer). Human collection is impossible at scale. A teacher LLM with access to tools (e.g., a sandboxed Python interpreter) can be prompted to solve problems step by step; every successful trajectory becomes training data. Why synthetic data fits: the tool itself verifies success (did the code run? did the search return the right page?), so filtering is nearly automatic. This is a fast-growing area (e.g., ToolLLM, AgentTuning). The main challenge is diversity of failure modes — a teacher that always uses the same tool order produces a brittle student.
2.9 Test-Time / Evaluation Set Augmentation

A subtler use: generating new evaluation sets that probe specific capabilities (math word problems of a particular difficulty, code tasks in a specific library). The problem solved: public benchmarks leak and saturate. Synthetic benchmarks, seeded from templates and verified by unit tests, provide fresh, controlled evaluation. Why synthetic data fits: you control difficulty and content exactly. The risk is "teaching to the test" — you must hold synthetic test sets independent of the training set (disjoint seeds, different teacher temperature) or your metric is meaningless. The card's benchmark_metrics (downstream delta vs no-synthetic baseline) is the right way to check.
2.10 Multilingual & Low-Resource Augmentation

For low-resource languages, teachers can translate existing high-quality instruction data (high-resource → low-resource) or generate natively in the target language. The problem solved: no parallel high-quality instruction data exists for most languages. Why synthetic data fits: the teacher's translation is the data. The main filter is round-trip consistency (translate EN → SW → EN and compare) plus a native-speaker LLM-as-judge. The card notes this fits its "cold start for rare languages" pro. Risk: teacher bias toward high-resource style (e.g., over-formal phrasing), which can make the model sound unnatural.
