1. Concept Summary (ELI5)

Imagine you are packing a lunchbox for a growing puppy. You don't just dump a whole bag of plain kibble in — that's boring and the puppy won't grow strong. Instead you mix the recipe: mostly kibble (web text), a big scoop of protein-rich meat (code), some vitamins (math), a few crunchy treats (books), and a sprinkle of different-flavored bits (other languages). Some days you start with the easy food and save the chewy stuff for later, just like a teacher who gives easy homework first and harder homework at the end of the term. That is Data Mixture & Curriculum Learning: instead of feeding a large language model every kind of text in equal amounts, we pick how often each kind of text appears (the mixture), and sometimes we order it from easy to hard (the curriculum). The result is a model that learns more capability per unit of compute — a "free lunch" paid for in statistics rather than GPUs.
2. Use Cases (8 real-world scenarios)
2.1 Llama-3 Pretraining Mixture

The Llama-3 8B and 70B models were pretrained on ~15T tokens drawn from a curated multi-domain corpus. Meta's technical report makes the mixture explicit: roughly 50% web text, ~25% code, ~10% math, ~10% books/papers, and ~5% multilingual. Without this mixture, a model trained on raw web data is fluent but weak at structured reasoning. The problem this solves is that a uniform sample over the raw web systematically under-represents code and math (they are <2% of web text) yet they drive the downstream capabilities customers actually pay for — writing working code, solving math problems, following multi-step instructions. The mixture up-weights these scarce-but-high-value domains while still retaining broad world knowledge from web text. Domain weights are tuned with DoReMi or gradient-based methods, then kept constant for most of training. This is the canonical example everyone copies, and the cost is essentially zero: no extra FLOPs, just a different probability of selecting each shard.
2.2 DeepSeek-R1 Late-Stage Math Up-Sampling

DeepSeek's reasoning models (DeepSeek-Math, DeepSeek-R1) do not use a single static mixture. They use a two-phase recipe: general pretraining on a balanced corpus (web, code, math, multilingual), followed by a late-stage up-sampling phase where math and code are given dramatically higher weight (often 40–60% of tokens). The problem is that a model trained at uniform-ish weights learns enough math to pass simple tests but not enough to reliably do chain-of-thought at test time. Late-stage up-sampling works because the model has already learned general language and world knowledge — pouring more math at the end sharpens reasoning without sacrificing fluency. The technique fits perfectly when the objective is a reasoning model, because the marginal value of a math token is much higher than the marginal value of yet another generic web paragraph. Practically this is implemented as a scheduler that switches sampling weights after a fixed number of tokens or after a validation-loss plateau; the switch itself is nearly free.
2.3 Phi-3 Small-Model Curriculum

Microsoft's Phi-3-mini (3.8B parameters) was trained on only ~3.3T tokens — much less than GPT-4-scale models — yet performs competitively on reasoning benchmarks. A key ingredient is a curriculum: the first phase uses general web + books to build broad language competence, then the second phase uses "textbook-quality" and heavily filtered code/math data to sharpen reasoning. Small models are particularly sensitive to training order — if you start with hard math, the loss spikes and the model can destabilize. Starting easy builds a stable base; ending hard concentrates learning capacity exactly where it matters. This use case demonstrates the curriculum half of the card: order matters as much as weights. The lesson is that at 3.8B parameters you cannot afford to waste any token, so every training step must be spent on data with high information density for that model size, which changes over training time.
2.4 Multilingual Pretraining Balance (BLOOM, Aya)

Multilingual models like BLOOM (46 natural languages) and Aya (101 languages) face an extreme version of the mixture problem. If you sample uniformly over web text, English dominates (~45%) and low-resource languages like Swahili or Telugu are almost invisible. If you sample uniformly over languages, low-resource languages get too many repeats and the model overfits on tiny corpora. Temperature-controlled mixing (p_i ∝ n_i^0.3 or 0.5) gives every language meaningful representation while still giving more tokens to languages with more data. The problem is that low-resource languages have three orders of magnitude less data than English but need to be usable, so a naive frequency-based mixture is unusable. A well-tuned temperature often gives 20–30% of tokens to non-English languages even though they are <5% of the raw data — a capability multiplier for global users at no extra compute cost.
2.5 Domain Adaptation via Continued Pretraining

Suppose you have a strong base model and want to adapt it to legal or medical text. Continued pretraining on a domain-weighted mixture is the standard approach: keep the base model's general knowledge alive by sampling ~70% original-pretraining-distribution data (web/code/math) and ~30% domain data (case law, PubMed). The problem: if you train only on domain data, the model undergoes catastrophic forgetting — it becomes great at citing statutes but loses the ability to hold a coherent multi-turn conversation. A temperature-controlled or DoReMi-style mixture solves this by preserving the base distribution. The recipe is architecture-agnostic and works for any base model. Because it is statistical (not architectural), you can start from any checkpoint without retraining from scratch, making it the cheapest route to domain specialization.
2.6 Data-Constrained Small-Model Training

When you're training a small model (say 100M–1B parameters) on a fixed token budget of 20B tokens, every token must earn its place. A uniform mixture over your available corpus wastes tokens on redundant web boilerplate. Temperature-controlled sampling (T ≈ 0.3) over-samples code/math by 3–5× and downsamples web by 2×, effectively tripling the "useful information" per token. The problem solved is that the token budget is hard-limited by compute cost — the mixture is the only free variable. Empirically, a well-tuned mixture gives 10–30% relative improvement on coding and math benchmarks at equal FLOPs, which is why it is standard practice at small-model scales (Phi, TinyLlama, SmolLM). This is the purest example of the card's promise: capability per compute.
2.7 Code-Focused Agent Training

An agent model that needs to use tools, write shell commands, and produce parseable JSON benefits enormously from code-heavy mixtures. Industry practice is often 30–50% code tokens for agentic models, far above the ~2% code fraction of raw web text. The problem this solves: agents fail on basic syntax and format errors if they haven't seen enough code, and those failures cascade into user-visible tool-call errors. Up-sampling code (and structured output formats embedded in code) reduces these failures at the source. Over-sampling carries a real risk (overfitting on small code corpora), so practitioners typically use a "code-weighted but not code-saturated" mixture — e.g., T = 0.5 with code as the largest domain — and monitor a held-out human-eval metric to catch overfitting early.
2.8 Compute-Optimal Training at Fixed FLOPs

Chinchilla-style scaling laws optimize model size and token count at fixed FLOPs. Data mixture optimization adds a second, orthogonal degree of freedom: at a given model size and token count, which tokens you see changes the final capability. Recent work (DoReMi, RegMix, Data Mixing Laws) treats the mixture as a hyperparameter to be optimized via small proxy runs. The problem solved is that practitioners cannot afford to run a 100k-GPU-hour pretraining to find out that 20% web was too much. Instead, they train a tiny reference model (500M params, 5B tokens) under candidate mixtures, extrapolate the optimal weights via a learned scaling law, and then apply those weights to the full run. This is now the state of the art for mixture tuning and is exactly what the card's "O(N) sampling; negligible overhead" complexity line implies: the sampler is free, the search is the actual cost.
